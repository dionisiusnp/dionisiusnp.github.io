Pipeline Pencarian Tiga Tier

Strategi multi-lapisan untuk menjawab pertanyaan secara efisien dan akurat

Mengapa Tiga Tier?

Setiap tier pencarian memiliki trade-off biaya vs. kualitas yang berbeda. Sistem dirancang untuk menggunakan sumber daya seminimal mungkin — hanya naik ke tier lebih mahal jika tier sebelumnya tidak memadai.

Tier 1 — FAQ Lokal (Gratis, Deterministik)

  • Pencarian berbasis kata kunci di tabel chatbot_faqs MySQL
  • Dikelola oleh admin via panel Laravel — tidak perlu sentuh kode
  • Respons instan, tidak ada biaya API, tidak ada latensi AI
  • Cocok untuk pertanyaan yang sudah diketahui pola jawabannya

Tier 2 — Pencarian Semantik Qdrant (Berbayar ringan, Kontekstual)

  • Pertanyaan diubah menjadi vektor 1536 dimensi menggunakan model embedding OpenAI
  • Dibandingkan dengan ribuan dokumen yang sudah di-embed di Qdrant via cosine similarity
  • Aktif jika skor cosine > 0.28 (threshold dapat dikonfigurasi)
  • Mampu menangkap pertanyaan yang diparafrase berbeda namun bermakna sama

Tier 3 — Web Scraping Real-time (Konteks terkini)

  • Menggunakan DuckDuckGo Search + BeautifulSoup untuk mencari informasi terbaru
  • Aktif hanya jika Tier 2 tidak mencapai skor kepercayaan minimal
  • Berguna untuk pertanyaan tentang jadwal, pengumuman, atau informasi yang sering berubah

Confidence Guard

Jika setelah ketiga tier skor kepercayaan gabungan masih di bawah 0.4, sistem tidak memaksakan jawaban — melainkan mengeskalasi ke admin manusia dan mengirim menu FAQ interaktif kepada pengguna.

Dual LLM — Lokal & Cloud

Pemilihan model AI otomatis berdasarkan ketersediaan dan anggaran

Dua Model, Satu Keputusan Otomatis

Sistem memiliki dua pilihan LLM yang diperlakukan sebagai primary dan fallback. Keputusan dilakukan per permintaan, bukan dikonfigurasi secara statis.

LLM Lokal — Ollama (llama3:8b)

  • Berjalan di server sendiri, tidak ada biaya token
  • Data tidak keluar ke pihak ketiga — privasi terjaga
  • Kapasitas: maks 6 proses paralel, maks 30 antrian aktif
  • Diprioritaskan selama antrian tidak penuh dan server sehat

LLM Cloud — OpenAI GPT-4o-mini

  • Diaktifkan otomatis jika Ollama penuh atau tidak tersedia
  • Biaya per token dipantau real-time, batas harian USD 5,00
  • Kualitas jawaban lebih tinggi untuk pertanyaan kompleks

Budget Guard sebagai Penentu Akhir

Sebelum memanggil LLM mana pun, sistem mengecek sisa anggaran harian. Jika batas telah tercapai, sistem tidak memanggil model apapun dan langsung mengeskalasi ke admin — mencegah tagihan tak terduga.

💰

Budget Guard Real-time

Mekanisme kontrol biaya otomatis untuk layanan AI berbayar

Komponen Biaya yang Dipantau

  • Biaya percakapan WhatsApp: Meta mengenakan biaya ~Rp 400 per sesi baru (24 jam window). Sistem mencatat setiap sesi baru.
  • Biaya token LLM cloud: OpenAI mengenakan biaya per token yang diproses. Sistem mencatat jumlah token input dan output setiap panggilan.
  • LLM lokal: Tidak ada biaya token, tetapi ada biaya infrastruktur server.

Alur Pemeriksaan Anggaran

  • Setiap pesan masuk → cek biaya sesi WA vs. batas harian (default Rp 150.000)
  • Sebelum panggil LLM cloud → cek biaya token vs. batas harian (default USD 5,00)
  • Jika salah satu terlampaui → bot offline, pengguna diarahkan ke admin
  • Batas dikonfigurasi via tabel settings di database, dapat diubah admin

Pencatatan untuk Analitik

Seluruh pemakaian dicatat di tabel chatbot_usages per hari. Data ini dapat dilihat melalui dashboard Laravel dan berguna untuk audit biaya bulanan dan perencanaan anggaran IT.

Takeover Percakapan oleh Admin

Mekanisme serah terima dari bot ke manusia secara mulus

Alur Takeover

  • Admin membuka riwayat chat calon mahasiswa di panel Laravel
  • Klik "Nonaktifkan Bot" → kolom is_bot_active di tabel chatbot_leads berubah ke false
  • Pesan berikutnya dari calon mahasiswa masuk ke Python → sistem cek flag → bot tidak membalas
  • Admin mengirim pesan dari panel Laravel → disimpan di chatbot_messages dengan role = 'admin'
  • Python mengirimkan pesan tersebut ke WhatsApp calon mahasiswa atas nama nomor kampus

Jenis Pesan yang Dapat Dikirim Admin

  • Teks biasa
  • Gambar, dokumen, audio, video (via URL)
  • Tombol interaktif (quick reply, URL, nomor telepon)

Batasan Jendela 24 Jam

Meta hanya mengizinkan pengiriman pesan bebas dalam jendela 24 jam setelah pengguna terakhir mengirim pesan. Di luar itu, hanya template yang disetujui Meta yang boleh digunakan. Sistem menegakkan aturan ini secara otomatis.

Broadcast Terjadwal

Pengiriman massal terpadu antara panel admin dan mesin pengiriman

Pembagian Peran dalam Broadcast

Ini adalah contoh paling nyata bagaimana Laravel dan Python bekerja dalam satu alur:

  • Laravel (konfigurasi): Admin memilih template, menentukan waktu kirim, mengunggah daftar target nomor HP via form web
  • MySQL (perantara): Data tersimpan di chatbot_broadcast_schedules dan chatbot_broadcast_targets
  • Python (eksekusi): Scheduler APScheduler mengecek database setiap menit. Saat waktu tiba, Python memanggil Meta API untuk mengirim pesan ke setiap target
  • MySQL (status): Python memperbarui status setiap target (PENDING → SENT atau FAILED beserta pesan error)
  • Laravel (monitoring): Admin dapat memantau progres dan status per penerima di panel

Template WhatsApp

Template dibuat via form visual di Laravel (header, body, footer, tombol, variabel dinamis), kemudian dikirim ke Meta untuk disetujui. Hanya template berstatus APPROVED yang dapat digunakan untuk broadcast.

Manajemen Knowledge Base

FAQ dan dokumen semantik yang dikelola admin, digunakan AI

FAQ — Basis Pengetahuan Terstruktur

  • Admin menambah/edit/nonaktifkan FAQ via CRUD Laravel tanpa perlu restart Python
  • Python membaca tabel chatbot_faqs secara langsung saat ada pesan masuk
  • Sistem sudah dilengkapi 100+ FAQ awal tentang: program studi, biaya, beasiswa, prosedur daftar, fasilitas kampus

Qdrant — Knowledge Base Semantik

  • Admin dapat menambah dokumen (PDF, konten web) melalui antarmuka Laravel
  • Dokumen di-embed oleh Python menjadi vektor dan disimpan di Qdrant
  • Admin dapat mencari dokumen, melihat daftar isi, dan menghapus dokumen yang usang
  • Python menggunakan koleksi Qdrant sebagai Tier 2 pencarian saat FAQ tidak cukup

Pembaruan Tanpa Downtime

Baik FAQ maupun dokumen Qdrant dapat diperbarui kapan saja oleh admin tanpa perlu me-restart layanan Python. Perubahan FAQ aktif langsung pada panggilan berikutnya.

Retrieval-Augmented Generation (RAG)

Arsitektur AI untuk sistem tanya-jawab berbasis dokumen

Konsep RAG dalam Sistem Ini

RAG adalah pendekatan di mana LLM tidak hanya mengandalkan pengetahuan bawaan modelnya, tetapi secara aktif mengambil dokumen relevan dari sumber eksternal terlebih dahulu, kemudian menggunakannya sebagai konteks saat menghasilkan jawaban. Hasilnya: jawaban lebih akurat, terverifikasi, dan tidak mengarang.

Implementasi Teknis

  • Embedding: Pertanyaan diubah ke vektor 1536 dimensi via text-embedding-3-small
  • Retrieval: Cosine similarity di Qdrant menemukan dokumen paling relevan
  • Augmentation: Dokumen relevan (score > 0.28) dikirim sebagai konteks ke prompt LLM
  • Generation: LLM merumuskan jawaban berdasarkan konteks — bukan memori model

Potensi Topik Penelitian

  • Evaluasi akurasi RAG vs. chatbot berbasis rule/FAQ murni dalam konteks PMB
  • Pengaruh kualitas dan kuantitas dokumen training terhadap relevansi jawaban
  • Optimasi threshold cosine similarity untuk domain Bahasa Indonesia / pendidikan tinggi
  • Perbandingan model embedding untuk teks Bahasa Indonesia

Hybrid LLM — Efisiensi Biaya AI

Strategi pengelolaan model AI di lingkungan sumber daya terbatas

Mengapa Ini Relevan untuk Riset?

Adopsi AI di institusi pendidikan, terutama perguruan tinggi swasta, sering terhambat oleh biaya operasional layanan cloud AI yang tidak terduga. Sistem ini menawarkan pendekatan hybrid sebagai solusi: gunakan model lokal selama mampu, eskalasi ke cloud hanya bila diperlukan.

Parameter Teknis

  • Ollama: gratis, privat, butuh GPU (VRAM ~6GB), latensi ~2-5 detik
  • OpenAI GPT-4o-mini: ~USD 0.0002/1K token, latensi ~1-2 detik, kualitas lebih tinggi
  • Pengambilan keputusan: berbasis ukuran antrian lokal bukan kualitas pertanyaan

Potensi Topik Penelitian

  • Perbandingan kualitas respons LLM open-source vs. proprietary untuk Bahasa Indonesia
  • Model penganggaran AI yang berkelanjutan untuk institusi pendidikan non-profit
  • Analisis trade-off privasi data vs. kualitas layanan pada deployment LLM lokal di kampus

Integrasi Sistem Heterogen via Database

Pola arsitektur untuk menghubungkan dua stack teknologi berbeda

Tantangan: Dua Bahasa, Satu Ekosistem

Python dan PHP adalah dua ekosistem yang berbeda dengan konvensi, framework, dan cara kerja masing-masing. Menghubungkan keduanya dalam satu sistem terpadu memerlukan strategi integrasi yang tepat.

Solusi: Database sebagai Lapisan Integrasi

Alih-alih membangun REST API internal atau message queue yang menambah kompleksitas, sistem ini menggunakan MySQL bersama sebagai satu-satunya titik pertukaran data. Ini sederhana, mudah di-debug, dan tidak menambah dependency jaringan internal.

Trade-off Desain

  • Keuntungan: Sederhana, tidak ada overhead jaringan antar service, data langsung konsisten, mudah dimonitor via SQL query
  • Risiko: Perubahan skema tabel berdampak ke kedua aplikasi sekaligus — perlu koordinasi saat migrasi

Potensi Topik Penelitian

  • Evaluasi pola integrasi sistem informasi akademik berbasis shared database vs. API-first
  • Strategi pengelolaan skema database dalam sistem multi-framework di lingkungan kampus
  • Analisis trade-off arsitektur untuk pengembangan sistem informasi di perguruan tinggi skala menengah

Chatbot AI dalam Layanan Akademik

Konteks Implementasi

Sistem ini tidak hanya prototipe — melainkan digunakan secara nyata di Universitas Dinamika untuk melayani pertanyaan calon mahasiswa baru (PMB). Pertanyaan yang ditangani mencakup prosedur pendaftaran, biaya kuliah, beasiswa, jalur masuk, dan informasi umum kampus.

Dimensi yang Dapat Diukur

  • Konsistensi: Setiap calon mahasiswa mendapat jawaban dari sumber resmi yang sama
  • Skalabilitas: Dapat melayani ratusan percakapan paralel tanpa tambahan staf
  • Akurasi: Dapat diukur dari rasio eskalasi ke admin (skor kepercayaan <0.4)

Potensi Topik Penelitian

  • Efektivitas chatbot AI berbasis WhatsApp dalam meningkatkan kualitas layanan PMB
  • Tingkat kepuasan calon mahasiswa terhadap respons chatbot vs. layanan manual
  • Dampak implementasi chatbot terhadap beban kerja staf PMB
  • Pola pertanyaan calon mahasiswa sebagai cerminan kebutuhan informasi pra-pendaftaran

Tata Kelola Anggaran AI Real-time

Mekanisme kontrol pengeluaran untuk keberlanjutan sistem AI

Permasalahan yang Diatasi

Layanan AI berbasis cloud (seperti OpenAI dan Meta WhatsApp API) dikenakan biaya per penggunaan. Tanpa kontrol yang tepat, lonjakan traffic atau kesalahan konfigurasi dapat menghasilkan tagihan yang jauh melebihi anggaran yang dialokasikan — masalah kritis untuk institusi pendidikan non-profit.

Mekanisme Kontrol Berjenjang

  • Budget Guard: Setiap panggilan layanan berbayar didahului pengecekan saldo harian
  • Hard Limit: Jika batas tercapai, sistem berhenti otomatis — tidak ada override
  • Reset Harian: Penghitung biaya direset setiap tengah malam WIB
  • Audit Trail: Semua pemakaian tercatat di chatbot_usages untuk laporan keuangan IT

Potensi Topik Penelitian

  • Model tata kelola anggaran AI yang berkelanjutan untuk perguruan tinggi Indonesia
  • Analisis biaya-manfaat implementasi chatbot AI di perguruan tinggi swasta
  • Kerangka kebijakan penggunaan AI yang bertanggung jawab di institusi pendidikan

Pemanfaatan platform pesan instan dalam komunikasi akademik resmi

Mengapa WhatsApp?

WhatsApp adalah aplikasi dengan penetrasi tertinggi di Indonesia (>90% pengguna smartphone). Calon mahasiswa tidak perlu mengunduh aplikasi baru, membuat akun, atau mempelajari antarmuka asing — mereka cukup mengirim pesan ke nomor kampus seperti biasa.

Kemampuan Teknis yang Dimanfaatkan

  • Interactive Messages: Menu list dan tombol quick reply untuk navigasi FAQ
  • Template Messaging: Broadcast pesan promosi resmi yang disetujui Meta
  • 24-hour Window: Jendela komunikasi bebas setelah pengguna memulai percakapan
  • Rich Media: Dukungan gambar, video, dan dokumen dalam satu percakapan

Keterbatasan yang Perlu Dicatat

  • Ketergantungan pada platform pihak ketiga (Meta) — rentan perubahan kebijakan
  • Biaya per sesi dapat signifikan pada volume tinggi
  • Template broadcast harus melewati proses persetujuan Meta sebelum dapat digunakan

Potensi Topik Penelitian

  • Efektivitas WhatsApp Business API vs. kanal digital lain (email, website, media sosial) untuk layanan PMB
  • Analisis pola respons calon mahasiswa terhadap komunikasi institusi via WhatsApp
  • Studi UX chatbot berbasis platform pesan instan dalam konteks pendidikan tinggi Indonesia
